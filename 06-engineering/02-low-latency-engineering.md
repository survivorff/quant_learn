# 02 · 低延迟工程

> **先说结论：我的策略不需要极低延迟。** 但我需要知道延迟从哪来、怎么测、什么时候它变成瓶颈。
>
> 更重要的是：**低延迟是机构面试的高频考点**，走 QD 路线必须能聊。

---

## 一、先判断：你真的需要低延迟吗

| 策略类型 | 延迟敏感度 | 需要的量级 |
|---|---|---|
| 日线趋势/截面动量 | 极低 | 秒级足够 |
| 资金费 carry | 极低 | 秒级足够 |
| 小时级均值回归 | 低 | 百毫秒 |
| 跨所价差（双边持仓） | 中 | 十毫秒 |
| 做市（宽价差、冷门标的） | 中高 | 毫秒 |
| 做市（主流币盘口竞争） | 高 | 亚毫秒 |
| 延迟套利 / HFT | 极高 | 微秒 + colocation |

**我的策略（低中频 + 结构性套利）落在前四行。** 这意味着：

- ✅ Python 完全够用
- ✅ 云服务器够用（选靠近交易所的区域）
- ❌ 不需要 colocation、内核旁路、FPGA

**但延迟仍然重要的地方**：
1. 撤单速度（避免逆向选择）
2. 极端行情时的反应（这时延迟长尾会暴露）
3. 跨所套利的单腿风险窗口

---

## 二、延迟链路分解

一笔交易的完整延迟路径：

```
[1] 交易所撮合 → 行情推送
[2] 网络传输（交易所 → 你）
[3] 内核接收 + 协议栈
[4] 解析（JSON/二进制）
[5] 本地订单簿更新
[6] 特征计算
[7] 策略决策
[8] 风控检查
[9] 订单序列化
[10] 网络传输（你 → 交易所）
[11] 交易所接收 + 风控 + 撮合
```

### 量级感觉（crypto CEX，云服务器）

| 环节 | 典型量级 |
|---|---|
| 网络往返（同区域） | 几毫秒 |
| 网络往返（跨大洲） | 数十到上百毫秒 |
| JSON 解析 | 微秒到几十微秒 |
| Python 策略逻辑 | 几十微秒到毫秒 |
| **交易所内部处理** | **几毫秒到几十毫秒，且波动大** |
| 极端行情时的交易所延迟 | **可能到秒级** |

### 关键洞察

**在 crypto CEX 上，交易所自身的处理延迟和波动，往往大于你能优化的部分。**

这意味着：
1. 把 Python 优化到 C++ 水平，可能只省下总延迟的 5%
2. **选择正确的服务器区域（减少网络往返）的收益，远大于代码优化**
3. 极端行情时交易所拥堵，你的优化完全失效 —— **这时唯一有效的是"提前减仓"而不是"更快反应"**

**优化顺序：地理位置 > 网络配置 > 架构设计 > 代码优化 > 换语言。** 大多数人反过来做。

## 三、测量（比优化更重要）

不测量的优化是猜测。

### 必须测的指标

| 指标 | 怎么测 |
|---|---|
| 行情延迟 | 交易所时间戳 vs 本地接收时间戳（注意时钟同步） |
| 处理延迟 | 接收 → 决策完成 |
| 下单延迟 | 发出 → 收到确认 |
| 端到端延迟 | 行情时间戳 → 订单被交易所接收 |
| **各环节的分布** | **P50 / P90 / P99 / P99.9 / max** |

### 关键：看分布，不看均值

```
均值 20ms 听起来不错
但 P99 = 2000ms 意味着 1% 的订单延迟 2 秒
而那 1% 往往集中在极端行情 —— 正是最关键的时刻
```

**长尾延迟决定了你的尾部损失。** 这是我在后端做性能优化的核心经验：优化 P99 比优化均值有价值得多。

### 时钟同步

跨机器测延迟需要时钟同步：
- 用 NTP（普通场景够用，毫秒级精度）
- 记录本地时钟与交易所时间戳的系统性偏差
- **不要假设交易所时间戳是精确的**（它可能是入队时间而非撮合时间）

## 四、优化手段（按性价比排序）

### 高性价比（先做这些）

| 手段 | 效果 |
|---|---|
| **服务器选在靠近交易所的云区域** | 可能省几十到上百毫秒 |
| 用 WebSocket 而非 REST 轮询 | 消除轮询延迟 |
| 长连接 + 连接复用 | 避免握手开销 |
| 只订阅需要的数据流 | 减少解析负担 |
| 增量更新而非全量快照 | 减少数据量 |
| 预计算与缓存 | 减少热路径计算 |
| 减少日志同步写 | 异步日志 |
| 避免热路径内存分配 | 对象池、预分配 |

### 中等性价比

| 手段 | 效果 |
|---|---|
| 二进制协议（如果交易所支持） | 减少解析开销 |
| 更快的 JSON 解析库（orjson 等） | 微秒级改善 |
| numba/Cython 加速热路径 | 显著但有限 |
| 单线程避免锁竞争 | 减少抖动 |
| CPU 绑核 / 关闭节能 | 减少抖动 |
| 调优内核网络参数 | 有限改善 |

### 低性价比（除非做 HFT）

| 手段 | 说明 |
|---|---|
| 内核旁路（DPDK/io_uring 极致优化） | 复杂度极高 |
| 自定义 TCP 栈 | 只有 HFT 需要 |
| FPGA / 硬件加速 | 机构级投入 |
| Colocation | crypto CEX 部分提供，成本高 |

**对我：只做"高性价比"那一栏，最多碰一点"中等"。**

## 五、抖动（jitter）比绝对延迟更麻烦

延迟稳定在 50ms 比"平时 5ms、偶尔 500ms"好得多。

### 抖动来源

| 来源 | 缓解 |
|---|---|
| GC（Python/Java） | 减少对象分配；Python 的 GC 可以调优或临时关闭 |
| 内存分配 | 预分配、对象池 |
| 磁盘 IO（日志） | 异步日志、内存缓冲 |
| 网络抖动 | 无法控制，只能测量并适应 |
| 上下文切换 | CPU 绑核、减少线程 |
| CPU 节能/降频 | BIOS 关闭节能模式 |
| 云主机的"邻居效应" | 用独占实例 |
| Python 全局解释器锁 | 单线程设计 |

### 面对抖动的策略设计

**接受抖动，而不是消除它。** 做法：
- 订单带价格保护（IOC + 最差价格），延迟大时自动放弃而不是以坏价格成交
- 用时间戳检查数据新鲜度，过期数据不用于决策
- 高延迟时主动降级（减少报价频率、拉宽价差、暂停开仓）
- 在策略里显式建模"我的信息可能过期"

**这一条比任何代码优化都重要**：一个能容忍延迟的策略，比一个依赖低延迟的策略稳健得多。

## 六、面试相关（走 QD 路线必须能聊）

机构面试常问的低延迟话题：

| 话题 | 要点 |
|---|---|
| 延迟链路分解 | 能画出完整路径并给出各环节量级 |
| P99 vs 均值 | 为什么长尾更重要 |
| 缓存友好的数据结构 | 数组 vs 链表、内存布局、false sharing |
| 无锁数据结构 | 环形缓冲、CAS、内存序 |
| 分支预测与流水线 | 热路径避免不可预测分支 |
| 内存分配 | 为什么热路径不分配、对象池 |
| GC 影响 | Java/Go 的 GC 停顿、如何规避 |
| 内核旁路 | 概念与适用场景 |
| 时钟与时间戳 | 单调时钟 vs 墙钟、PTP vs NTP |
| 订单簿数据结构 | 如何设计高效的 LOB（数组索引 vs 树） |

### 我的准备策略

- **不吹自己做过 HFT**（会被问穿）
- **强调"我理解延迟工程的原理，并且在高并发系统上有实战优化经验"**
- 用 Java 的性能优化经验类比（JVM 调优、GC 优化、缓存友好设计）
- 强调 P99 优化、故障注入、可观测性的实战经验 —— **这些机构真正在意**
- 诚实说明"我的策略不需要微秒级，我选择了正确的复杂度"

**诚实的能力边界描述，比夸大更有说服力。** 面试官能分辨。
