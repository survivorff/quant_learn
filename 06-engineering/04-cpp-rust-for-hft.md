# 04 · 何时需要换语言：Rust / C++

> **先说结论：短期我不需要换语言。** 但需要知道边界在哪，以及走 QD 路线时怎么补这块。
>
> 换语言是**最后**的优化手段，不是第一个。

---

## 一、判断是否需要换语言

### 决策流程

```
Python 慢了？
├── 是不是算法/架构问题？    → 先修架构（99% 的情况）
├── 是不是可以向量化？        → numpy/polars
├── 是不是热路径循环？        → numba
├── 是不是可以并行？          → 多进程
├── 是不是 IO 瓶颈？          → asyncio，换语言没用
└── 以上都试过还不够 → 考虑换语言（只换热路径，不是全部）
```

### 什么时候真的需要

| 场景 | 为什么 Python 不够 |
|---|---|
| 亚毫秒级做市报价 | Python 的抖动（GC、解释器）超过预算 |
| 高吞吐订单簿维护（每秒数十万更新） | 解释器开销累积 |
| 大规模回测（几千标的 × tick 级） | 单纯的计算量 |
| 需要严格的延迟上界 | Python 无法给出确定性保证 |

### 什么时候不需要

| 场景 |
|---|
| 日线/小时级策略 |
| 资金费 carry、跨所价差（双边持仓） |
| 因子研究与回测（用向量化 + numba） |
| 数据采集与存储（IO 瓶颈） |

**我的策略都在"不需要"这一栏。**

## 二、Rust vs C++（如果要选）

| 维度 | Rust | C++ |
|---|---|---|
| 性能 | 相当 | 相当 |
| **内存安全** | **编译期保证** | 靠纪律和工具 |
| 并发安全 | 编译期防数据竞争 | 容易出错 |
| 生态（量化） | 增长快（`nautilus_trader` 用 Rust 内核） | 传统机构主流，库更全 |
| 学习曲线 | 陡（所有权/借用/生命周期） | 陡（且陷阱更多） |
| 编译速度 | 慢 | 慢 |
| 与 Python 集成 | `PyO3` / `maturin`，体验好 | `pybind11`，可用 |
| 机构使用 | 新兴，逐渐增加 | 传统 HFT 主流 |
| 招聘市场 | 需求增长 | 稳定需求 |

### 我的选择：Rust

理由：
1. **内存安全的编译期保证**在交易系统里价值极高 —— 一个内存 bug 可能造成资金损失
2. **`PyO3` 与 Python 的集成体验好**，适合"Python 主体 + Rust 热路径"的混合架构
3. `nautilus_trader` 用 Rust 内核，我要读它的源码，学 Rust 顺路
4. 从 Java 转 Rust 的心智负担，比转 C++ 小（不用同时学 C++ 的历史包袱）
5. Crypto 生态里 Rust 使用广泛（Solana、多个 L1、MEV 工具链）

**但如果面试传统金融机构，C++ 仍是硬通货。** 需要至少能读懂 C++ 代码并聊清概念。

## 三、混合架构（推荐路线）

```
┌─────────────────────────────────────┐
│  Python 层                           │
│  - 策略逻辑（迭代快）                 │
│  - 因子研究                          │
│  - 配置与编排                        │
│  - 监控与报告                        │
└──────────────┬──────────────────────┘
               │ PyO3 绑定
┌──────────────▼──────────────────────┐
│  Rust 层（热路径）                    │
│  - 订单簿维护                        │
│  - 行情解析                          │
│  - 特征计算（热点）                   │
│  - 回测事件循环                      │
└─────────────────────────────────────┘
```

### 迁移的正确顺序

1. **先用 Python 把逻辑跑对**
2. **profile 找出真正的热点**（不要猜）
3. **只把热点用 Rust 重写**
4. **写测试验证 Rust 版本与 Python 版本结果一致**（bit-level 一致）
5. 逐步扩大 Rust 的范围（如果需要）

第 4 步最容易被跳过，但它是防止"优化引入 bug"的唯一手段。

**反面教训：不要一开始就用 Rust 写全部。** 研究阶段需要快速迭代，Rust 的编译时间和心智负担会拖慢你 3 倍。

## 四、需要掌握的核心概念（不必精通语言）

即使不写生产级 Rust/C++，这些概念必须理解（面试会问，且能改善 Python 代码）：

| 概念 | 为什么重要 |
|---|---|
| 栈 vs 堆 | 决定分配开销 |
| 内存布局与缓存行 | 数据结构性能的根本 |
| **缓存友好的数据结构** | 数组 > 链表；结构体数组 vs 数组结构体（SoA/AoS） |
| False sharing | 多线程性能杀手 |
| 分支预测 | 热路径避免不可预测分支 |
| 内存序（memory ordering） | 无锁编程的基础 |
| 无锁数据结构 | 环形缓冲区、CAS |
| 零拷贝 | 减少数据搬运 |
| RAII / 所有权 | 资源管理 |
| 内存池 / 预分配 | 避免热路径分配 |

### 这些概念在 Python 里也有用

- 缓存友好 → 用 numpy 连续数组而非 Python 列表
- 避免热路径分配 → 预分配数组，复用对象
- 分支预测 → 向量化替代条件循环
- 零拷贝 → 用 memoryview / Arrow

**理解底层，能让你写出更快的 Python。**

## 五、Rust 学习路线（如果要学）

| 阶段 | 内容 | 目标 |
|---|---|---|
| 1 | 所有权、借用、生命周期 | 能读懂代码 |
| 2 | trait、泛型、错误处理 | 能写小工具 |
| 3 | `PyO3` + `maturin` | 能给 Python 写扩展 |
| 4 | 实现一个订单簿 | 有实际产出 |
| 5 | 读 `nautilus_trader` 内核源码 | 学生产级设计 |
| 6 | 异步（tokio）、并发 | 能写完整服务 |

**建议的第一个项目：用 Rust 实现订单簿维护 + 通过 PyO3 暴露给 Python，benchmark 对比纯 Python 版本。**

这个项目的价值：
- 范围小，能完成
- 有明确的性能对比（可量化的成果）
- 是真实需要的组件
- **是面试时可以展示的作品**

## 六、时间投入的判断

诚实评估：学 Rust 到能写生产代码，需要几个月的持续投入。

| 选项 | 收益 | 成本 |
|---|---|---|
| 不学 Rust，专注策略与研究 | 更快出实盘结果 | QD 面试少一个筹码 |
| 学 Rust，做一个订单簿组件 | 面试筹码 + 理解底层 | 1-2 个月业余时间 |
| 全面转 Rust 重写系统 | 性能 | 3-6 个月，且可能不需要 |

### 我的决定

```
阶段一到三：不碰 Rust，专注把策略和研究流水线跑通
阶段四（有实盘数据后）：花 1-2 个月做"Rust 订单簿 + PyO3"这一个项目
不做：用 Rust 重写整个系统
```

**理由：现阶段的瓶颈是"没有验证过的策略"，不是"系统太慢"。** 优化不存在的瓶颈是最典型的时间浪费。

如果转向 QD 求职（见 [`07-career-and-capital`](../07-career-and-capital/)），再把 Rust/C++ 的优先级提上来。
