## 解决什么问题

现成的回测框架大多不满足 crypto 的需求（资金费、强平、阶梯保证金），而且用现成框架你不知道它在什么地方对你撒谎。

自己写一个，目标是：**架构上物理性地无法访问未来数据**，并且完整建模 crypto 特有机制。

---

## 目标

### 核心组件

- [ ] **DataFeed**：多标的多数据源的归并排序，产出严格按时间排序的事件流
- [ ] **EventLoop**：单线程按时间推进；固定同时间戳事件优先级
- [ ] **Strategy**：只通过回调接收数据（不能直接查 DataFrame）
- [ ] **ExecutionSimulator**：分级成本模型（L1 → L3 可配置）
- [ ] **Portfolio**：持仓、资金、PnL（整数最小单位）
- [ ] **RiskEngine**：限额检查，独立于策略
- [ ] **Recorder**：每笔订单、每次成交、每时点净值

### Crypto 必需组件（最重要）

- [ ] **资金费结算事件**（按周期收付）
- [ ] **强平检查**（每 bar 检查保证金率，触发则强制平仓）
- [ ] **保证金计算**（阶梯保证金、全仓/逐仓）
- [ ] **标记价格**（强平和未实现盈亏用标记价）
- [ ] **合约精度与最小下单量**
- [ ] **交易暂停/下架处理**

> **没有资金费和强平的 crypto 回测，结果是无意义的。** 这是最常被忽略、影响最大的两项。

### 订单管理

- [ ] 订单状态机（含部分成交、拒单、超时撤销）
- [ ] 订单类型：Limit、Limit IOC、Limit FOK、Post-only、Reduce-only
- [ ] 资金与保证金约束

## 设计决策与取舍（关键）

### 1. 成交时点：为什么用 t+1 开盘

| 方案 | 问题 |
|---|---|
| 当前 bar 收盘价成交 | **未来函数**：收盘时才知道收盘价 |
| **下一 bar 开盘价成交** | **默认选择**，保守且真实 |
| 下一 bar VWAP | 更真实但需 bar 内数据 |

### 2. 同时间戳事件的优先级（必须固定）

```
资金费结算 > 强平检查 > 行情更新 > 成交回报 > 策略回调
```

不固定 = 结果不可复现。

### 3. 成本模型分级

| 级别 | 模型 | 适用 |
|---|---|---|
| L1 | 固定手续费 + 固定 bps 滑点 | 低频最低要求 |
| L2 | 手续费 + 半个实际价差 + 平方根冲击 | 中频基线 |
| L3 | 用真实 L2 深度逐档吃单 | 中高频必须 |

先实现 L1 和 L2，L3 等 lab-01 采到深度数据后加。

### 4. 延迟建模

用**实测延迟分布采样**，不用固定值。理由：长尾（P99）决定尾部损失，固定均值会完全掩盖它。

## 怎么验证正确性（8 项自测，全部必须通过）

| 测试 | 方法 | 期望 |
|---|---|---|
| **零信号** | 策略永不下单 | PnL 严格 = 0 |
| **买入持有** | 第一天买入并持有 | PnL = 标的收益 − 一次手续费 |
| **未来函数** | 在未来某点插入极端异常值 | 该点之前的 PnL **完全不变** |
| **成本零化** | 手续费滑点设 0 | PnL = 理想 PnL |
| **确定性** | 同配置跑两遍 | 结果 bit-level 一致 |
| **精度** | 跑 10 万笔交易 | 资金与逐笔累加一致，无浮点漂移 |
| **强平** | 构造极端行情 | 强平正确触发，损失符合手算 |
| **资金费** | 已知费率与持仓 | 手算与回测一致 |

**"未来函数测试"最有价值** —— 它能自动发现绝大多数信息泄漏。
