# 03 · 风险管理与回撤

> 风险管理不是"少赚一点换安全"，而是**"确保你能活到策略生效"**。
>
> 大多数策略的期望是正的但方差巨大。在这种情况下，**生存本身就是收益**。

---

## 一、风险类型清单（crypto 版）

不只是"价格会跌"。完整清单：

| 类型 | 具体 | 能否用金融手段对冲 |
|---|---|---|
| **市场风险** | 方向、波动率、相关性变化 | ✅ 可对冲/可分散 |
| **流动性风险** | 想平仓时没有对手方；滑点放大 | ⚠️ 部分（限制仓位） |
| **杠杆/强平风险** | 保证金不足被强平 | ✅ 保证金管理 |
| **对手方风险** | **交易所跑路/被黑/冻结提币** | ❌ 只能分散 + 限额 |
| **执行风险** | 错单、重复下单、状态不一致、单腿成交 | ❌ 工程问题 |
| **技术风险** | 系统宕机、网络中断、API 变更 | ❌ 工程问题 |
| **模型风险** | 策略假设失效、过拟合、参数漂移 | ⚠️ 监控 + 熔断 |
| **操作风险** | 私钥泄露、误操作、配置错误 | ❌ 流程与权限控制 |
| **合规/监管风险** | 政策变化、账户被限制 | ❌ 分散司法辖区 |
| **智能合约风险** | 合约漏洞、经济攻击 | ❌ 限制敞口 |
| **尾部/跳跃风险** | 插针、暴跌、脱锚 | ⚠️ 期权对冲或降杠杆 |

### 关键观察

**表里"不能用金融手段对冲"的项（对手方、执行、技术、操作）占了一半，而且它们是我最容易低估的。**

个人量化交易者的真实死因统计，大概率不是"策略不赚钱"，而是这几项：
- 交易所出事
- 系统 bug 导致的错单
- 私钥泄露
- 配置错误导致的意外仓位

**这些全是工程和流程问题。这也意味着：我的后端工程背景在风控上的价值，大于在 alpha 上的价值。**

## 二、限额体系

### 分层限额（自上而下检查）

```yaml
# 每一层都是硬约束，任何一层超限就拒绝下单
account:
  max_gross_exposure: 1.0x
  max_net_exposure: 0.8x
  max_daily_loss_pct: 3
  max_drawdown_pct: 15

venue:
  max_capital_pct: 40           # 单交易所
  min_margin_ratio: 3.0x        # 保证金充足率下限

strategy:
  max_capital_pct: 40
  max_drawdown_pct: 10
  max_daily_trades: 100         # 防止 bug 导致的疯狂下单

symbol:
  max_exposure_pct: 20
  max_correlated_group_pct: 50

order:
  max_notional: ___
  max_pct_of_depth: 20
  max_slippage_bps: 30
  min_notional: ___             # 防止精度问题产生的微小订单
```

### 实现要点（工程）

1. **风控引擎独立于策略**，在订单发出前拦截
2. **风控检查是同步的、阻塞的**，不能"先下单再检查"
3. **风控状态持久化**，重启后不丢失（日内亏损、当日交易数）
4. **风控失败时的默认行为是拒绝**（fail-safe，不是 fail-open）
5. **风控参数变更需要审计日志**
6. `max_daily_trades` 这条很重要：**能防住"bug 导致无限循环下单"这类灾难**

第 6 条是我从后端限流经验里最想强调的一点：**很多灾难不是策略错，是循环没退出。**

## 三、三级熔断

预先定义，触发即执行，不许临时判断。

### 一级：减仓（黄灯）

| 触发条件 | 动作 |
|---|---|
| 日内亏损达到上限的 50% | 新开仓仓位减半 |
| 组合波动率超过目标 1.5 倍 | 按比例减仓到目标 |
| 单策略回撤达到限额 70% | 该策略仓位减半 |
| 保证金充足率低于阈值 | 减仓到安全水平 |

### 二级：停止开新仓（橙灯）

| 触发条件 | 动作 |
|---|---|
| 日内亏损达到上限 | 停止当日所有新开仓，只允许平仓 |
| 单策略回撤达到限额 | 停止该策略，平掉其仓位 |
| 数据异常（行情中断/明显错误） | 停止所有开仓 |
| 交易所异常（拒单率上升/延迟飙升） | 停止该所开仓 |
| 实盘-回测偏差超过阈值 | 停止并排查 |

### 三级：全部平仓并停机（红灯）

| 触发条件 | 动作 |
|---|---|
| 总回撤达到上限 | 全部平仓，停止系统，强制复盘 |
| 检测到状态不一致（本地 vs 交易所） | 停止下单，人工介入 |
| 检测到重复下单/错单 | 立即停机 |
| 安全事件（密钥可能泄露） | 立即平仓 + 撤销 API 权限 |
| 交易所出现风险信号 | 提币 + 平仓 |

### 熔断后的恢复流程

**不允许"看起来没事了就重启"。** 必须：
1. 写复盘文档（原因、影响、修复）
2. 修复根因（不是重启了事）
3. 在模拟盘验证修复
4. 小仓位恢复，观察期 N 天
5. 逐步恢复到正常仓位

## 四、区分"正常回撤"与"策略失效"（最难的判断）

这是 [`00-README.md`](./00-README.md) 出口标准第 7 题的答案。

### 为什么难

- 策略正常状态下也会有长期亏损（趋势策略的水下期可能长达数年）
- 真正失效时，你只有很少的数据能证明它
- 统计上，需要很长时间才能区分"夏普 0.8 的策略正在回撤"和"夏普 0 的策略"

### 可操作的判断框架

**第一层：预先知道正常范围**

在上线前，从回测中提取：
| 指标 | 记下这个数字 |
|---|---|
| 历史最大回撤 | |
| 历史最长水下时长 | |
| 历史最大连续亏损次数 | |
| 回撤的分布（用 CPCV 的多条路径） | |

**如果当前回撤仍在历史范围内，那是正常的，不许干预。**

**第二层：结构性证据（比统计更可靠）**

不看"亏了多少"，看"逻辑还成立吗"：

| 检查 | 例子 |
|---|---|
| 收益来源的前提是否消失 | 资金费长期转负 → carry 策略前提消失 |
| 市场结构是否改变 | 交易所改费率、新产品上线、监管变化 |
| 因子 IC 是否衰减 | 监控因子的滚动 IC，不只看策略 PnL |
| 拥挤度是否上升 | 价差收窄、OI 变化 |
| 协整关系是否断裂 | 滚动协整检验失败 |
| 执行质量是否下降 | 成交率、滑点、成本占比 |

**结构性证据比 PnL 更早、更可靠地告诉你策略失效了。** 因为 PnL 噪声太大，而结构性变化是可观察的。

**第三层：统计检验**

用序贯检验（sequential testing）：
```
H0: 策略夏普 = 回测夏普
H1: 策略夏普 = 0
随着数据累积，计算似然比，超过阈值则拒绝 H0
```

这比"回撤超过 X% 就停"更有统计依据，但需要较长时间。

### 我的实操规则

```
1. 回撤在历史范围内 + 无结构性证据 → 继续，不干预
2. 回撤在历史范围内 + 有结构性证据 → 减仓并加强监控
3. 回撤超出历史范围 × 1.5 → 停止，强制复盘
4. 有明确结构性失效证据 → 立即停止，不管回撤多少
```

**第 4 条最重要**：如果你知道逻辑已经不成立了，就不要因为"还没亏够止损线"而继续。

## 五、压力测试

见 [`03-research-infra/05-evaluation-metrics.md`](../03-research-infra/05-evaluation-metrics.md) 的完整场景表。这里强调 crypto 特有的：

| 场景 | 具体 |
|---|---|
| 单日 -50% | crypto 历史上发生过 |
| 交易所宕机 4 小时 | 无法平仓，持仓裸露 |
| **提币暂停** | 资金锁在交易所 |
| 稳定币脱锚 10% | 保证金价值缩水 |
| 资金费反向到历史极值 | carry 策略变成付费 |
| 连环强平 | 深度抽空，滑点放大 10 倍 |
| API 限流/密钥失效 | 无法操作 |
| **所有策略同时最大回撤** | ρ = 1 假设 |

### 一条关键规则

> **任何单一压力场景导致的损失，必须小于你的总回撤上限。**
>
> 如果某个场景会让你损失超过承受范围，那不是"低概率风险"，是"必须现在就降低的暴露"。

## 六、操作安全（最容易被忽视）

| 项 | 规则 |
|---|---|
| API 密钥 | 只开必要权限（**绝不开提币权限**）；IP 白名单；定期轮换 |
| 密钥存储 | 不入 git；用系统 keychain 或 KMS；不明文放配置文件 |
| 私钥（链上） | 硬件签名或 KMS；热钱包限额；主资金冷存储 |
| 权限分离 | 只读监控账号 vs 交易账号分开 |
| 配置变更 | 版本控制 + 审核；生产配置与测试配置严格隔离 |
| 部署 | 灰度、可回滚；不在市场活跃时段部署 |
| 二次确认 | 大额操作、参数变更需要二次确认 |
| 备份与恢复演练 | 定期演练：如果服务器挂了，多久能恢复 |
| 提币演练 | 定期真实提币一次，验证通道畅通 |

### API 权限的具体建议

```
交易机器人的 API key：
✅ 读取行情
✅ 读取账户
✅ 下单/撤单
❌ 提币（绝对不要开）
❌ 划转到其他账户（除非策略必需，且要 IP 白名单）
```

**"绝不开提币权限"这一条能防住"密钥泄露导致资金被盗"这个最严重的场景。** 即使密钥泄露，攻击者最多只能乱交易（有损失但不会归零）。
