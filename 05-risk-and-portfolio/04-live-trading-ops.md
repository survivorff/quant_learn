## 二、监控指标

### 必须实时监控 + 告警

| 类别 | 指标 | 告警条件 |
|---|---|---|
| **存活** | 心跳 | 超过 N 秒无心跳 |
| **数据** | 行情延迟 | > 阈值 |
| | 行情中断 | 超过 N 秒无更新 |
| | 数据异常（价格跳变/零值） | 检测到即告警 |
| **执行** | 下单成功率 | < 阈值 |
| | 拒单率 | > 阈值 |
| | 下单延迟 P99 | > 阈值 |
| | 错单数 | > 0 立即告警 |
| **持仓** | 实际持仓 vs 目标持仓偏差 | > 阈值 |
| | 保证金充足率 | < 阈值 |
| | 单标的敞口 | 超限 |
| **盈亏** | 日内 PnL | 达到熔断阈值 |
| | 当前回撤 | 达到熔断阈值 |
| **一致性** | 本地状态 vs 交易所状态 | 不一致立即告警 |
| **系统** | CPU / 内存 / 磁盘 / 网络 | 常规阈值 |

### 需要每日检查（不一定告警）

| 指标 | 关注什么 |
|---|---|
| 在线率 | 策略实际运行时长 / 应运行时长，目标 > 99% |
| **实盘-回测偏差** | 同期实盘收益 vs 回测预期，偏差来源归因 |
| 成本占毛收益比例 | 趋势是否恶化 |
| maker 成交占比 | 执行质量 |
| 滑点分布 | 与预期对比 |
| 因子 IC（滚动） | 是否衰减 |
| 各策略的风险贡献 | 是否偏离风险预算 |
| 资金分布 | 各交易所占比是否超限 |

### 告警的工程要求

- **分级**：P0 立即电话/推送，P1 消息，P2 日报
- **去重与抑制**：同一问题不要刷屏
- **可操作**：告警内容要包含"该做什么"，不只是"出错了"
- **测试**：**告警系统本身要定期测试**（静默失败的告警系统比没有告警更危险）

最后一条是我在后端最深的教训：**没被验证过的告警，等于没有告警。**

## 三、状态一致性与对账

这是交易系统最核心的工程问题。

### 三个状态源

```
1. 策略的意图状态（我想要什么仓位）
2. 系统的记录状态（我认为我有什么仓位/挂单）
3. 交易所的真实状态（实际有什么）
```

**任何两者不一致都是危险信号。**

### 对账机制

| 频率 | 内容 | 不一致时 |
|---|---|---|
| 实时（每次成交回报） | 更新本地状态 | 序列号校验 |
| 每分钟 | 挂单列表对比 | 撤销孤儿单 |
| 每分钟 | 持仓对比 | 偏差 > 阈值则告警 |
| 每小时 | 资金余额对比 | 告警 |
| 每日 | 完整对账（成交明细、手续费、资金费） | 生成对账报告 |

### 不一致的常见原因

| 原因 | 处理 |
|---|---|
| 成交回报丢失 | 定期全量拉取补齐 |
| 网络超时但订单实际已提交 | **用 client_order_id 幂等**，重试时先查询 |
| 重启期间的成交 | 启动时全量同步 |
| 手动干预 | 记录，并让系统能识别外部变更 |
| 强平/ADL | 系统必须能感知并更新状态 |

### 幂等性设计（关键）

```python
# 每笔订单必须有客户端生成的唯一 ID
client_order_id = f"{strategy}_{symbol}_{timestamp}_{seq}"

# 下单超时后不要直接重试，先查询
def safe_place_order(order):
    try:
        return place(order)
    except Timeout:
        existing = query_order_by_client_id(order.client_order_id)
        if existing:
            return existing              # 已经提交了，不要重复下单
        return place(order)              # 确认未提交才重试
```

**"超时后直接重试"是最常见的重复下单原因。** 这一条能防住一整类灾难。

## 四、故障处理 SOP

预先写好，故障时按流程走，不临场发挥。

### 通用原则

```
1. 先止血（停止新开仓），再排查
2. 优先保证"不产生新的错误"，而不是"立刻恢复运行"
3. 不确定时，选择更保守的动作（平仓 > 持仓，停止 > 继续）
4. 全程记录，事后复盘
```

### 具体场景

| 故障 | 立即动作 | 后续 |
|---|---|---|
| 行情中断 | 停止开新仓；已有仓位按预设规则（持有或平仓） | 排查数据源；切换备用源 |
| 下单持续失败 | 停止策略；检查是否有未确认的订单 | 排查 API/网络/权限 |
| 状态不一致 | **立即停止下单**；不要试图"自动修复" | 人工核对，手动纠正后再启动 |
| 交易所宕机 | 停止该所所有操作；评估裸露敞口 | 考虑在其他所对冲 |
| 保证金不足告警 | 自动减仓到安全水平 | 排查为什么会到这一步 |
| 疑似错单/重复下单 | **立即停机** | 全量对账；修复根因 |
| 疑似密钥泄露 | 立即撤销 API key；平仓；转移资金 | 全面安全审计 |
| 交易所风险信号 | 提币；平仓 | 重新评估该所敞口 |

### "状态不一致时不要自动修复"

这条反直觉但重要：自动修复逻辑在状态未知的情况下可能造成更大损失（比如重复平仓、反向开仓）。

**规则：状态不一致 → 停止 → 人工确认 → 手动纠正 → 重启。**

## 五、每日复盘（最高杠杆的动作）

复盘不是"看看赚了多少"，是**系统性地提取信息**。

### 每日复盘模板

```markdown
## 日期：____

### 系统健康
- 在线率：___%
- 异常事件数：___（每个都要写清原因）
- 告警数：___
- 状态不一致次数：___

### 执行质量
- 订单数 / 成交数 / 拒单数：
- maker 占比：___%
- 平均滑点：___ bps（vs 预期 ___）
- 成本占毛收益：___%

### 盈亏
- 各策略 PnL：
- **PnL 归因**：方向 / carry / 执行成本 / 资金费
- 实盘 vs 回测预期偏差：___，来源：

### 风险
- 当前回撤：
- 各标的敞口：
- 保证金充足率：
- 是否触发任何限额/熔断：

### 发现的问题
1.
2.

### 今日的一个改进
（只写一个，明天执行）
```

### 关键：PnL 归因

不要只看总 PnL，要拆开：
```
总 PnL = 信号带来的 PnL（理论）
        − 执行成本（滑点 + 手续费）
        ± 资金费
        ± 执行偏差（未成交/延迟造成的差异）
```

**只有做了归因，你才知道"这个月亏钱"是策略问题还是执行问题。** 这两者的应对完全不同。

### 情绪记录

在交易日志里记录情绪状态（想干预吗？焦虑吗？想加仓吗？）。

理由：见 [`03-research-infra/03-backtest-pitfalls.md`](../03-research-infra/03-backtest-pitfalls.md) 第 11 类。你未来的自己需要这些数据来认识自己的行为模式。

模板见 [`journal/trade-journal-template.md`](../journal/trade-journal-template.md)。

## 六、部署与环境

| 项 | 建议 |
|---|---|
| 服务器位置 | 靠近交易所的云区域（降低延迟）；但别过度优化 |
| 冗余 | 关键组件双活或快速故障转移 |
| 时钟 | NTP 同步；记录与交易所时间的偏差 |
| 配置管理 | 版本控制；生产/测试严格隔离 |
| 部署方式 | 容器化；灰度；可秒级回滚 |
| 部署时机 | **不在市场活跃时段部署** |
| 日志 | 结构化日志；集中收集；保留足够长时间 |
| 数据备份 | 交易记录、配置、状态定期备份 |
| 环境隔离 | 测试网密钥与生产密钥物理隔离，防止误用 |

### 一条经验

**先在测试网/模拟盘上把工程做扎实，再上真钱。** 真钱环境下调试 bug 的代价是工程代价的几十倍。
